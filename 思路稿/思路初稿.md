# 格律约束解码：技术方案文档

## 1. 核心理念

### 1.1 目标
让大模型生成严格符合《词林正韵》格律的古典诗词，通过**约束解码（Constrained Decoding）**技术，在生成过程中动态干预模型输出，确保**字数、句读、平仄、押韵**100%合规。

### 1.2 核心思想 (贪婪 + 查表)
> **在模型采样下一个字之前，干预其概率分布，将不符合格律的候选字概率强制置零。**

传统生成方式：
模型计算概率 → 采样 → 输出字 → （事后检查格律，可能不合规）

约束解码方式：
模型计算概率 → [格律检查与干预] → 过滤后采样 → 输出字 → （必定合规）

---

## 2. 关键概念

### 2.1 处理时机 logits之后的softmax概率化计算后，归一化之前
模型对每个候选字的**原始打分**（softmax归一化前的数值）。约束解码操作的对象。

### 2.2 Token与字的关系
- **Token**：模型处理的基本单元，可以是单个汉字，也可以是多个汉字组成的词，因此模型输出可能不符合传统断句
- **解决方案**：在模型输出前进行检查，剪枝不合规token

### 2.3 硬约束 vs 软约束
| 类型 | 做法 | 本方案选择 |
|------|------|-------|
| 硬约束 | 非法字概率置为-∞（强制为0） | 目前方案  |
| 软约束 | 非法字概率大幅惩罚（如×0.01） | 未来考虑  |

## 3. 系统架构

### 3.1 数据层

#### 3.1.1 《词林正韵》数据库
**数据结构**如下
```json
{
  "第一部": {
    “平声”: {
          "东",
          "同",
          "童",
          ...
    },
    "仄声": {...},
  },
  "第二部": {...},
  ...
}
```

#### 3.1.2 词牌格律库
每个词牌定义：
- **总字数**：全词字数
- **断句位置**：明确的句读划分（如"一曲/新词/酒一杯"）
- **每位置约束**：每个字位置的平仄要求（平/仄/韵/可平可仄）
- **押韵位置**：需押韵的字位及韵部要求
- **数据结构**如下：
```json
{
    "浣溪沙": {
      "variant": "default",  // 是否为变格
      "number_of_stanzas": 2,  // 几片
      "stanza1": {
        "num_lines": 3,
        "num_chars": 21,
        "chars_per_line": [
            7,
            7,
            7
        ],
        "rhyme_positions": [    // 末尾需要押韵的句子序号 
            3                   // 表示第三句最后一个字需要押韵
        ],
        "lines": [
            "中仄/平平/仄仄平",
            "中平/中仄/仄平平",
            "中平/中仄/仄平平"
        ]
    },
    "stanza2": {
      "num_lines": 3,
      "num_chars": 21,
      "chars_per_line": [
        7,
        7,
        7
      ],
      "rhyme_positions": [  
        2,
        3
      ],
      "lines": [
        "中仄/中平/平仄仄",
        "中平/中仄/仄平平",
        "中平/中仄/仄平平"
      ]
    },
    "rhyme_type": "平韵"
    }
}
```


### 3.2 约束引擎

#### 3.2.1 单步解码流程
输入：当前已生成文本、当前位置、词牌名

1. 查询格律
```
   └─ 当前位置的字数要求（1字/2字/...）
   └─ 当前位置的平仄要求（平/仄/韵/不限）
   └─ 当前位置是否押韵
```

2. 查询韵书
- 根据平仄/韵部要求，获取合法汉字集合

3. 构建Token掩码
```
   └─ 遍历模型词表，筛选同时满足：
      ├─ 解码后为单字（len(decode(token)) == 1）
      └─ 该字在合法汉字集合中
   └─ 合法token保留原logits，非法token设为-∞
```

4. 采样输出
```
   └─ Softmax归一化过滤后的概率分布
   └─ 采样得到下一个token
   └─ 解码为汉字，追加到生成文本
```

5. 位置推进，循环至生成完成

#### 3.2.2 句读控制机制
- 数据结构中已将断句用 `/` 明确标注
- 约束解码首先获取当前字数位置的断句要求，例如第一次断句前有两个字，则剪枝token中三个字以上的结果。
- 接下来根据平仄要求进一步剪枝，确保模型输出满足平仄规则。
- 举例：《浣溪沙》第一句。
例如第一个断句前有两个字，就把token中字数大于三的剪枝掉，
接下来再把平仄不对的再剪枝掉，模型第一次输出为“一”。
那么检查断句前只有一个字，那么接下来模型第二次输出就必须是一个字，
约束解码继续两步剪枝，
模型输出“曲”。模型第三次输出前，看断句，需要两个字，再进行两步剪枝，
模型输出了“新词”（假设在词划分中，“新词”被划分为了一个token，
因此被一次输出），满足句读，go on……


### 3.3 关键算法逻辑（状态机与动态过滤）
本质上是一个**“贪心+严格查表”**的局部过滤机制，通过维护生成状态来进行精准剪枝。

#### 1. 状态追踪 (State Tracking)
在生成过程中，需要动态维护以下核心变量：
- **当前句读剩余字数**：当前 `/` 分隔的片段还差几个字填满。
- **格律指针**：指向当前正在匹配的平仄规则（如“中仄/平平”的第2个字）。
- **韵部状态**：记录第一处押韵确立的韵部，后续押韵位置强制锁定该韵部。

#### 2. 三步过滤规则 (Token Filtering)
对于词表中的每一个候选 Token，执行以下判定，任意一步失败则将该 Token 对应的 Logits 设为 `-inf`：
- **规则 A（长度匹配）**：Token 解码后的汉字长度 $L \le$ `当前句读剩余字数`。防止越界输出。
- **规则 B（逐字平仄）**：将 Token 的 $L$ 个汉字逐一与格律指针向后的 $L$ 个平仄要求比对。若有任何一字平仄不符，直接否决整个多字 Token。
- **规则 C（押韵收束）**：若该 Token 恰好填满某句的最后一个押韵位，且之前已定韵脚，则该字必须属于已锁定的《词林正韵》韵部。若未指定韵脚，则第一个可以不受限，之后的韵脚服从第一个韵部。

#### 3. 状态推进 (State Advance)
模型最终采样出一个合法 Token 后，`剩余字数` 减少 $L$，`格律指针` 后移 $L$。若当前片段剩余字数为0，光标无缝跳转至下一个句读片段。

## 4. 约束掩码计算（查表性能优化）
如果在每次解码步都实时遍历几万到十几万规模的模型词表（Vocabulary）并执行查字典、解字符串等操作，推理速度将极其低下。因此采用**“离线预处理 + 运行时查表”**的掩码生成方案。

### 4.1 离线预建索引 (Offline Pre-processing)
在项目初始化/模型加载阶段，只执行一次：遍历整个大模型的词表，预先解码所有纯中文 Token，并查表获取其全局平仄属性。
构建一个高效的多维哈希索引，例如映射结构如下：
- `(长度: 1, 平仄: "平")` -> `{TokenID_1, TokenID_2, ...}`
- `(长度: 2, 平仄: "平平")` -> `{TokenID_A, TokenID_B, ...}`

*(注：在这个阶段同时将英文字母、特殊标点、甚至残缺字节（Byte Fallback Token）彻底过滤，确保候选池纯净。)*

### 4.2 运行时掩码生成 (Runtime Masking)
在单步解码的 Masking 阶段，将动态计算转换为集合提取：
1. **明确当前需求**：结合当前剩余字数和目标平仄（如：最多剩2个字，分别允许 `(1, "平")` 或 `(2, "平平")`）。
2. **集合提取与取并集**：从预建索引中，直接通过键提取对应的所有合法 Token ID 集合，进行并集运算。
3. **Logits 修改**：创建一个形状等于 `[vocab_size]` 且全为 `-inf` 的张量屏蔽图（Mask Tensor），仅通过 `scatter` 或高级索引操作在合法 Token ID 位置写入原大模型的 Logits。
4. **交还采样**：交还修改后的 Logits 给推断引擎进行 Softmax 运算，实现极其高效的硬约束采样。
